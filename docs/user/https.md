# HTTPS

По умолчанию сервер работает по HTTP: API-ключи передаются по сети открытым текстом.
Для сетей, где трафик может быть перехвачен, включите HTTPS в **Настройки → HTTPS**.

## Режимы сертификата

| Режим | Описание |
|---|---|
| Самоподписанный | Создаётся автоматически при первом включении и хранится в `<папка данных>\tls\` (`cert.pem`, `key.pem`). Действует 10 лет. В сертификат включаются имена `localhost`, имя компьютера, `127.0.0.1` и IPv4-адреса сетевых интерфейсов. |
| Свой сертификат | Пути к файлам цепочки сертификатов и закрытого ключа в формате PEM. Подходит для сертификатов, выпущенных доверенным центром или внутренним ЦС. |

После сохранения настроек сервер перезапускается и принимает подключения только по `https://`. В шапке окна адрес сервера показывается со схемой.
Если сертификат не удаётся загрузить, сервер не запускается: в шапке появляется «Ошибка сервера», а причина видна в настройках.

## Доверие к самоподписанному сертификату

Клиенты по умолчанию не доверяют самоподписанному сертификату. Варианты:

- **Сверить отпечаток.** В настройках показан отпечаток SHA-256 сертификата. Клиентское приложение может закрепить его (certificate pinning).
- **Отключить проверку на клиенте** — только для тестов, например `curl -k` или `Invoke-WebRequest -SkipCertificateCheck`.
- **Добавить сертификат в доверенные** на клиентском устройстве (`cert.pem`).

```bash
curl -k -X POST https://192.168.1.10:8765/flow/sleep/ -H "Authorization: Bearer rha_..."
```

## Новый сертификат

Кнопка **Создать новый сертификат** (или `remote-http-action-cli.exe tls regenerate`) заменяет самоподписанный сертификат и перезапускает сервер.
Клиенты, закрепившие прежний отпечаток, должны обновить его.

## Reverse proxy

Если HTTPS обеспечивает reverse proxy, оставьте в приложении HTTP. Добавьте адрес прокси в «Доверенные reverse proxy» (см. [Настройки](settings.md#сетевой-доступ)).
